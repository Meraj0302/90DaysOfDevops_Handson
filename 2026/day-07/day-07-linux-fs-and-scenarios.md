# Day 07 – Linux File System Hierarchy & Scenario-Based Practice

---

## Part 1: Linux File System Hierarchy

---

### `/` (Root Directory)

**What it contains:** The top-level directory of the entire Linux file system. Every other directory and file originates from here.

```bash
ls -l /
# You'll see: bin, etc, home, root, var, tmp, usr, opt, proc, sys, dev, ...
```

**I would use this when...** I need to navigate to any part of the system — it's the starting point for all absolute paths.

---

### `/home` – User Home Directories

**What it contains:** Personal directories for each regular user on the system. Each user gets their own subdirectory (e.g., `/home/ubuntu`, `/home/john`).

```bash
ls -l /home
# Example output: drwxr-xr-x ubuntu  john  alice
```

**I would use this when...** I need to find or manage a user's personal files, scripts, or configuration (like `.bashrc`, `.ssh/`).

---

### `/root` – Root User's Home Directory

**What it contains:** The home directory specifically for the `root` (superuser) account. Kept separate from `/home` for security reasons.

```bash
ls -la /root
# You'll see: .bashrc  .profile  .ssh/  .bash_history
```

**I would use this when...** I'm performing administrative tasks as root and need to access root's personal configurations or SSH keys.

---

### `/etc` – Configuration Files

**What it contains:** System-wide configuration files for the OS and installed applications. This is where almost all software stores its settings.

```bash
ls -l /etc
# You'll see: hostname  passwd  fstab  ssh/  nginx/  apt/  crontab  hosts
```

```bash
cat /etc/hostname
# Output: my-server
```

**I would use this when...** I need to configure a service (e.g., edit `/etc/nginx/nginx.conf`), manage users (`/etc/passwd`), or check network settings (`/etc/hosts`).

---

### `/var/log` – Log Files ⭐ (Very Important for DevOps!)

**What it contains:** Log files generated by the OS and running services. This is the first place to look when something goes wrong.

```bash
ls -l /var/log
# You'll see: syslog  auth.log  kern.log  dpkg.log  apt/  nginx/  docker/
```

```bash
# Find the largest log files
du -sh /var/log/* 2>/dev/null | sort -h | tail -5
```

**I would use this when...** Troubleshooting a failed service, investigating security incidents, or checking application errors in production.

---

### `/tmp` – Temporary Files

**What it contains:** Temporary files created by the OS and applications. This directory is typically cleared on every reboot.

```bash
ls -l /tmp
# You'll see: various temp files, sockets, lock files
```

**I would use this when...** I need a safe place to download/store files temporarily during a script or installation, knowing they'll be cleaned up automatically.

---

### `/bin` – Essential Command Binaries

**What it contains:** Core system binaries (commands) that are available to all users, even in single-user/recovery mode. Commands like `ls`, `cp`, `mv`, `cat` live here.

```bash
ls -l /bin
# You'll see: bash  cat  cp  ls  mkdir  mv  rm  echo  grep
```

**I would use this when...** Verifying whether a basic command exists on the system, or understanding what tools are available in a minimal environment.

---

### `/usr/bin` – User Command Binaries

**What it contains:** Non-essential user commands and applications installed on the system. Most of the programs you use daily are here (e.g., `git`, `python3`, `curl`).

```bash
ls -l /usr/bin
# You'll see: git  python3  curl  wget  vim  nano  htop
```

**I would use this when...** Looking for where an installed application's binary lives (e.g., running `which python3` points to `/usr/bin/python3`).

---

### `/opt` – Optional / Third-Party Applications

**What it contains:** Software installed outside the standard package manager — often large third-party tools like custom Java installations, proprietary software, or manually compiled apps.

```bash
ls -l /opt
# You may see: google/  containerd/  aws/  custom-app/
```

**I would use this when...** Installing or managing software that doesn't fit into the standard `/usr` hierarchy — like a custom monitoring agent or a vendor-supplied application.

## Part 2: Scenario-Based Practice

---

### Scenario 1: Service Not Starting

**Problem:** A web application service called `myapp` failed to start after a server reboot.

---

**Step 1:**
```bash
systemctl status myapp
```
**Why:** This gives an immediate overview — whether the service is `active`, `failed`, or `inactive`. The output includes recent log lines that often point directly to the error.

---

**Step 2:**
```bash
journalctl -u myapp -n 50
```
**Why:** Shows the last 50 log lines specific to `myapp`. This is where you'll find the actual error message — missing config file, port conflict, permission error, etc.

---

**Step 3:**
```bash
systemctl is-enabled myapp
```
**Why:** Tells us if `myapp` is set to start automatically on boot. If it says `disabled`, that's why it didn't restart after reboot.

---

**Step 4:**
```bash
journalctl -u myapp --since "1 hour ago"
```
**Why:** Narrows logs to the time window around the reboot/failure to avoid noise from older entries.

---

**Step 5 (if needed — enable and restart):**
```bash
sudo systemctl enable myapp
sudo systemctl start myapp
systemctl status myapp
```
**Why:** Enables the service on boot, starts it now, and confirms it's running.

---

**What I learned:** Always start with `systemctl status` for a quick overview, then dive into `journalctl` for the detailed error. Check `is-enabled` to catch boot-time issues.

---

### Scenario 2: High CPU Usage

**Problem:** The application server is slow. You SSH in and need to identify the culprit process.

---

**Step 1:**
```bash
top
```
**Why:** Shows a live, updating view of all processes sorted by CPU usage by default. Look at the top rows — the highest `%CPU` value is your suspect. Press `q` to quit.

---

**Step 2:**
```bash
ps aux --sort=-%cpu | head -10
```
**Why:** A non-interactive snapshot of the top 10 CPU-consuming processes. More useful in scripts or when you want to log the output. Note the `PID` column.

---

**Step 3:**
```bash
htop
```
**Why:** A more user-friendly, color-coded version of `top`. Easier to read. Use arrow keys to navigate, `F6` to sort by CPU, `F9` to kill a process.

---

**Step 4 (investigate the top process):**
```bash
# Replace <PID> with the actual Process ID from step 1/2
ls -l /proc/<PID>/exe
cat /proc/<PID>/cmdline
```
**Why:** Reveals exactly which binary and command is consuming the CPU. Helps confirm whether it's a legitimate app or something unexpected.

---

**What I learned:** `top` and `ps aux` are your first tools. Note the PID of the offending process, then investigate it with `/proc/<PID>/` for deeper context.

---

### Scenario 3: Finding Service Logs

**Problem:** A developer asks: "Where are the logs for the `docker` service?"

---

**Step 1:**
```bash
systemctl status docker
```
**Why:** Confirms that `docker` is a systemd-managed service and shows the most recent log lines right in the output.

---

**Step 2:**
```bash
journalctl -u docker -n 50
```
**Why:** Shows the last 50 lines of logs for the `docker` service. `journalctl` is the standard tool for all systemd-managed service logs.

---

**Step 3:**
```bash
journalctl -u docker -f
```
**Why:** The `-f` flag follows the log in real-time (like `tail -f`). Very useful when you're actively debugging and want to watch log output as it happens.

---

**Step 4 (filter by time):**
```bash
journalctl -u docker --since "2025-01-01 00:00:00" --until "2025-01-01 01:00:00"
```
**Why:** Useful when debugging a specific incident — narrow logs to the exact time window of the problem.

---

**What I learned:** For any systemd service, `journalctl -u <service-name>` is the go-to command. Use `-n` for recent lines, `-f` for live tailing, and `--since`/`--until` for time-based filtering.

---

### Scenario 4: File Permissions Issue

**Problem:** `/home/user/backup.sh` gives "Permission denied" when executed with `./backup.sh`.

---

**Step 1: Check current permissions**
```bash
ls -l /home/user/backup.sh
```
**Why:** Displays the permission string. A file without execute permission looks like `-rw-r--r--` — notice there is no `x` anywhere. That's the problem.

---

**Step 2: Add execute permission**
```bash
chmod +x /home/user/backup.sh
```
**Why:** The `+x` flag adds execute permission for the owner, group, and others. This is the standard fix for "Permission denied" on a script.

---

**Step 3: Verify the fix**
```bash
ls -l /home/user/backup.sh
```
**Why:** Confirm the permission string now shows `x` — it should look like `-rwxr-xr-x`.

---

**Step 4: Run the script**
```bash
./backup.sh
```
**Why:** Test that the script now executes without errors.

---

**Bonus — restrict to owner only (more secure):**
```bash
chmod 700 /home/user/backup.sh
# Result: -rwx------  (only the owner can read, write, and execute)
```

---

**What I learned:** "Permission denied" on a script almost always means the `x` (execute) bit is missing. Use `ls -l` to diagnose and `chmod +x` to fix. Think about whether all users need execute permission or just the owner.

## Summary: Why This Matters for DevOps

| Skill | Real-World Use |
|---|---|
| Knowing `/var/log` | First stop when something breaks in production |
| Knowing `/etc` | Every config change happens here |
| `systemctl` + `journalctl` | 80% of service debugging flows through these |
| `top` / `ps aux` | Diagnosing performance issues under pressure |
| `chmod` / `ls -l` | Fixing deployment failures caused by permissions |
